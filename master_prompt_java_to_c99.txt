# MASTER-PROMPT
## Разработка учебного компилятора подмножества Java в ANSI C99 (ISO/IEC 9899:1999)

# 1. Роль и основная задача

Ты — опытный разработчик компиляторов, специалист по языкам программирования, системному программированию на C и реализации runtime-систем.

Твоя задача — спроектировать и реализовать на Python полноценный учебный компилятор подмножества Java в ANSI C99 (ISO/IEC 9899:1999).

Компилятор переводит исходный код Java-подобного языка в исходный код C99. Для выполнения программ используется отдельная runtime-библиотека на C99.

Это полноценный компилятор, а не транслитератор. Требуются лексический, синтаксический и семантический анализ, промежуточное представление, генерация кода и runtime-система.

Не принимай самостоятельно архитектурные или семантические решения, которые уже определены в этом документе. Не заменяй согласованные правила привычными правилами Java, C++ или C.

Если обнаружишь реальное противоречие, техническую невозможность или недостаток информации, сначала объясни проблему и предложи конкретные варианты решения. Не маскируй проблему упрощением реализации.

Не создавай фиктивную поддержку возможностей языка.

# 2. Общие требования

## 2.1. Назначение

Компилятор предназначен для изучения принципов построения компиляторов и реализации объектно-ориентированного языка.

Поддерживаются:

- классы и объекты;
- одиночное наследование классов и множественное наследование интерфейсов;
- интерфейсы;
- виртуальные методы;
- перегрузка методов и конструкторов;
- примитивные типы;
- строки;
- одномерные массивы;
- строгая система типов;
- сборка мусора;
- генерация C99-кода.

Главные приоритеты: корректность семантики, предсказуемость поведения и надёжность.

## 2.2. Языки, платформы и стандарт

Компилятор реализуется на Python 3.10 или новее. Генерируемый код и Runtime
пишутся на ANSI C99 / ISO/IEC 9899:1999. Запрещена обязательная зависимость
от Windows, MinGW-w64, GCC, конкретного ABI, направления роста стека или
нестандартных расширений компилятора.

Сгенерированный код должен собираться любым C-компилятором, соответствующим
C99, при наличии необходимых свойств целевой платформы. Для Java-целых
использовать <stdint.h> и проверять наличие int8_t/int16_t/int32_t/int64_t;
на экзотических платформах без exact-width типов предусмотреть документированный
программный fallback либо явную ошибку сборки, не обещая невозможной
абсолютной переносимости. Аппаратные float/double разрешены при совместимости
с IEEE 754 binary32/binary64; при несовместимости необходим fallback или
явная диагностика ограниченной численной совместимости.

В C99 разрешены объявления по месту использования, //-комментарии, stdint.h,
stdbool.h, snprintf и другие стандартные возможности C99. Не использовать
C11/C17/C23-only API и неопределённое поведение C. Рекомендуемая проверка
GCC/Clang: -std=c99 -pedantic-errors -Wall -Wextra; для другого C99-компилятора
предусмотреть эквивалентный процесс сборки.

Полная документация типов, методов и синтаксиса Java для сверки:
https://metanit.com/java/tutorial/
Этот источник справочный: объём поддержки и намеренные отличия задаёт
настоящее ТЗ, а не весь Java API.

## 2.4. Интерфейс командной строки

Основная команда:

`python -m compiler.main input.java -o output.c`

Компилятор должен:

1. Прочитать исходный файл.
2. Выполнить лексический анализ.
3. Выполнить синтаксический анализ.
4. Построить AST.
5. Выполнить семантический анализ.
6. Построить типизированное IR.
7. Сгенерировать C99-код.
8. Создать необходимые `.c` и `.h` файлы.

Генерация C и компиляция C — отдельные этапы; связывание допускается любым компилятором C99.

Предусмотри выбор выходного каталога и имени файла.

# 3. Архитектура компилятора

## 3.1. Обязательный pipeline

Java source
→ Lexer
→ Parser
→ AST
→ Semantic Analyzer
→ Symbol Tables
→ Type Checker
→ IR Builder
→ Typed Intermediate Representation
→ C99 Code Generator
→ Generated C Source
→ Runtime Library
→ GCC
→ Executable

Генерация C непосредственно из AST запрещена.

Между AST и C Code Generator обязательно находится типизированное промежуточное представление — IR.

IR содержит разрешённые имена, типы, ссылки на символы, информацию о диспетчеризации методов и сведения о явных преобразованиях.

## 3.2. Модульность

Минимальная структура:

- `compiler/`
  - `__init__.py`
  - `main.py`
  - `lexer.py`
  - `tokens.py`
  - `parser.py`
  - `ast_nodes.py`
  - `semantic.py`
  - `symbol_table.py`
  - `type_system.py`
  - `ir.py`
  - `ir_builder.py`
  - `codegen.py`
  - `errors.py`

- `runtime/`
  - `runtime.h`
  - `runtime.c`
  - отдельные платформенные модули при необходимости.

- `tests/`
- `examples/`
- `README.md`

Структуру можно расширять, если это улучшает разделение ответственности.

Не объединяй весь компилятор в один большой файл.

## 3.3. Промежуточное представление

IR должен быть типизированным.

Для каждой операции должны быть известны:

- тип результата;
- типы операндов;
- целевые символы;
- явные преобразования;
- способ вызова метода;
- способ обращения к полю;
- единственный родительский тип, если применимо; сведения о GC-корнях и static-полях.

Семантические ошибки должны обнаруживаться до генерации C.

## 3.4. Оптимизация

Оптимизация не обязательна в первой версии.

Не выполняй преобразования, способные изменить наблюдаемое поведение.

# 4. Поддерживаемый язык

## 4.1. Классы

Поддерживаются:

- объявление классов;
- поля;
- методы;
- конструкторы;
- `new`;
- `this`;
- `super`;
- наследование;
- абстрактные классы;
- финальные классы.

Все классы имеют корневой тип `Object` через одну цепочку наследования.

Поддерживается единый компилируемый набор исходников без полноценной системы Java packages/import.

Имена типов разрешаются через таблицу символов всего набора исходников.

## 4.2. Одиночное наследование классов

Java-класс имеет не более одного непосредственного родительского класса.
Синтаксис: class C extends A implements I, J. При отсутствии extends
родитель — Object. Запись class C extends A, B запрещена.

Множественное наследование классов, повторяющиеся классовые подобъекты,
ромбовидные схемы классов, квалификаторы obj.Parent.member,
super.Parent(...) и branch-specific VTable из прежней архитектуры исключить.
У объекта ровно один базовый заголовок Object, содержащий динамический тип
и данные Runtime/GC. Все объектные ссылки имеют единое C-представление void*.

Поля собственного класса скрывают одноимённые унаследованные поля.
Поиск методов идёт по единственной цепочке родителей. Перегрузка разрешается
по точному совпадению типов аргументов. Переопределение заменяет соответствующий
слот единственной VTable класса; сигнатура и тип результата должны совпадать,
доступ не должен сужаться, final-метод переопределять нельзя.

Для вызова родителя использовать super.method(). Конструктор вызывает
super(args) первым оператором. Если явного вызова нет, компилятор вставляет
super() и требует доступный конструктор родителя без аргументов. Если у класса
не объявлены конструкторы, синтезировать конструктор по умолчанию с super().
Инициализация: выделение и обнуление всех полей, конструктор родителя,
инициализаторы полей текущего класса, остальное тело конструктора.
this(args) можно оставить неподдерживаемым с явной диагностикой.

Все обычные методы экземпляра виртуальны; при вызове из конструктора действует
динамический тип создаваемого полного объекта. Object.toString/equals/getClass
используют ту же единую цепочку наследования без специальных «первых ветвей».
Абстрактный класс не создаётся через new; конкретный класс реализует все
абстрактные методы; final-класс нельзя наследовать.

## 4.3. Интерфейсы

Поддерживаются объявление интерфейсов, множественное наследование интерфейсов
через extends, реализация нескольких интерфейсов классом через implements,
вызовы через интерфейсную ссылку и instanceof. Пример:
interface I3 extends I1, I2 { void m(); }
class C extends B implements I1, I2 { ... }

Интерфейсы содержат только абстрактные методы: без полей, default- и
static-методов. Равные сигнатуры в нескольких интерфейсах создают одно
обязательство реализации. Интерфейсы наследуются также через родительский
класс. Отдельные интерфейсные таблицы отображают сигнатуры на методы
фактического класса; одну VTable классов и интерфейсные таблицы не смешивать.
В интерфейсном графе проверять циклы, доступность и полноту реализации.
Приведение к интерфейсу требуется явно, как и другие ссылочные преобразования.

# 5. Примитивные типы и преобразования

Поддерживаются восемь примитивных типов:

- `byte`;
- `short`;
- `int`;
- `long`;
- `float`;
- `double`;
- `char`;
- `boolean`.

Размеры:

- byte — 8 бит;
- short — 16 бит;
- int — 32 бита;
- long — 64 бита;
- char — Unicode scalar value (32-битное представление uint32_t), согласно разделу 11.

boolean — самостоятельный логический тип.

## 5.1. Целочисленная арифметика

Переполнение реализуется с Java-подобной модульной семантикой.

Не допускай неопределённого поведения C при знаковом переполнении.

При необходимости используй runtime helper-функции.

## 5.2. Float и double

Используй программную модель IEEE 754 binary32 и binary64.

Поддерживай:

- обычные арифметические операции;
- NaN;
- положительную и отрицательную бесконечность;
- знаковый ноль;
- сравнения;
- преобразования.

Полная бит-в-бит идентичность всех редких случаев округления не обязательна. Обычные операции должны иметь согласованную документированную семантику.

## 5.3. Литералы

Поддерживаются:

- десятичные целочисленные литералы;
- шестнадцатеричные целочисленные литералы;
- суффиксы `L`/`l`;
- float с `F`/`f`;
- double с `D`/`d`;
- строковые и символьные литералы;
- boolean;
- `null`.

Проверяй допустимые диапазоны.

## 5.4. Запрет неявных преобразований

**Все неявные преобразования запрещены.**

Это относится к:

- числовым типам;
- float/double;
- char;
- boolean;
- ссылочным типам;
- классам;
- интерфейсам;
- аргументам методов;
- присваиваниям;
- возвращаемым значениям;
- тернарному оператору.

Запрещено автоматическое числовое продвижение.

Запрещено автоматическое расширение типа.

Запрещено автоматическое приведение к родителю или интерфейсу.

Если типы различаются, пользователь должен написать явное приведение.

### 5.4.1. Операции

Для арифметических и битовых операций типы операндов должны совпадать.

Для сравнения чисел типы операндов должны совпадать.

Для тернарного оператора типы обеих ветвей должны совпадать.

Для `&&`, `||`, `!` разрешён только boolean.

Числа не преобразуются в boolean.

Строковая конкатенация `+` поддерживается для `String + String`.

Преобразование примитивов в строки должно выполняться явно.

### 5.4.2. Null

`null` — специальное значение ссылочного типа.

`null` разрешён для любого ссылочного типа, включая классы, интерфейсы и массивы.

Это специальное правило совместимости null не является разрешением неявных преобразований между ссылочными типами.

Присваивание одного ссылочного типа другому по-прежнему требует точного совпадения типов либо явного приведения.

### 5.4.3. Явные приведения

Поддерживаются явные приведения:

- между числовыми примитивами;
- между совместимыми ссылочными типами;
- к интерфейсам;
- вниз по иерархии наследования с runtime-проверкой.

Целочисленные преобразования имеют документированную семантику усечения/сохранения младших битов.

Float/double в целые преобразуются с усечением к нулю.

NaN и бесконечности обрабатываются по Java-подобным правилам преобразования.

Явное приведение ссылки вниз выполняет runtime-проверку.

Если целевой обычный предок представлен несколькими подобъектами и неоднозначность известна из типов, приведение запрещается на этапе компиляции.

Приведение к Object всегда однозначно.

## 5.5. Типовая система

Используй структурные объекты типов, а не сравнение типов по строковым именам.

Различай:

- примитивные типы;
- ссылочные типы;
- классы;
- интерфейсы;
- массивы;
- String;
- null;
- void.

Проверка типов должна быть централизована.

# 6. Операторы и выражения

Поддерживаются:

- `+`, `-`, `*`, `/`, `%`;
- `==`, `!=`, `<`, `>`, `<=`, `>=`;
- `&&`, `||`, `!`;
- унарные `+`, `-`;
- `++`, `--`;
- `?:`;
- приведения;
- `instanceof`;
- доступ к полям;
- вызовы методов;
- индексация массивов;
- `=`, `+=`, `-=`, `*=`, `/=`, `%=`;
- `&`, `|`, `^`, `~`;
- `<<`, `>>`, `>>>`.

Приоритет и ассоциативность соответствуют Java для поддерживаемых конструкций.

`&&` и `||` используют короткое замыкание.

Тернарный оператор вычисляет только выбранную ветвь.

Порядок вычисления выражений — слева направо.

Нельзя менять порядок вычислений, если это меняет наблюдаемое поведение.

Деление на ноль — runtime error.

Остаток от деления имеет знак делимого.

Сдвиги реализуют Java-подобные правила.

`>>>` — логический правый сдвиг.

Для float/double учитываются NaN и знаковый ноль.

`==` и `!=` для объектов и массивов сравнивают идентичность ссылок.

Для String:

- `==` сравнивает ссылки;
- `equals` сравнивает содержимое.

# 7. Управляющие конструкции

Поддерживаются:

- блоки;
- `if`;
- `if/else`;
- `while`;
- классический `for`;
- foreach по одномерным массивам;
- `break`;
- `continue`;
- `return`.

Метки не поддерживаются.

`break` и `continue` относятся к ближайшему циклу.

Все пути non-void метода должны возвращать значение.

Недостижимый код — ошибка компиляции.

Foreach последовательно обходит одномерный массив, а переменная цикла получает значение очередного элемента.

# 8. Области видимости

Используются лексические блочные области видимости.

Локальная переменная не может повторно объявлять видимую локальную переменную в пересекающейся области.

После завершения блока его локальные переменные становятся недоступны.

Таблица символов должна поддерживать вложенные области.

# 9. Точка входа

Единственная точка входа:

`public static void main(String[] args)`

Другие варианты main не являются точкой входа.

`args` — массив String.

Аргументы командной строки декодируются в Unicode и сохраняются в UTF-8.
Для POSIX-окружений ожидается UTF-8 argv; для иных окружений использовать
отдельный адаптер ввода аргументов без зависимости остального Runtime от ОС.

Статические методы, кроме main и встроенных API, не поддерживаются; статические поля поддерживаются.

# 10. Массивы

Поддерживаются только одномерные массивы.

Полностью запрещены:

- многомерные массивы;
- массивы массивов;
- jagged arrays;
- частичное выделение размерностей;
- вложенные типы массивов.

Примеры:

- `new int[10]`;
- `new String[5]`;
- `new MyClass[3]`.

Массивы могут содержать все примитивные типы, String, ссылки на классы и интерфейсы.

Каждый массив — отдельный runtime-объект.

Массивы передаются и возвращаются по ссылке.

У массива есть поле `.length`.

Значения по умолчанию:

- числовые — ноль;
- boolean — false;
- char — `\u0000`;
- ссылочные — null.

Литералы массивов `{1, 2, 3}` не поддерживаются.

Индексация проверяет границы.

Выход за границы — runtime error.

`==` сравнивает ссылки.

Не вводи неявную совместимость типов массивов.

При записи ссылочного значения в массив выполняй runtime-проверку допустимости элемента.

GC должен сканировать ссылочные элементы.

# 11. Строки, UTF-8 и идентификаторы

Исходные файлы — строгий UTF-8. UTF-16LE/BE не поддерживать; UTF-8 BOM
необязателен и может быть пропущен. Runtime хранит String как неизменяемую
последовательность UTF-8 байтов. Unicode допустим в строковых и символьных
литералах, но НЕ в идентификаторах.

Идентификаторы пользовательских классов, интерфейсов, полей, методов,
параметров и переменных: [A-Za-z_$][A-Za-z0-9_$]* (кроме одиночного _ и
зарезервированных ключевых слов). Не-ASCII в имени — лексическая ошибка.

В этом учебном подмножестве char — Unicode scalar value диапазона
U+0000..U+10FFFF, за исключением U+D800..U+DFFF; представлять как uint32_t.
Это намеренно отличается от 16-битного Java char. String.length(),
charAt(index) и substring(begin,end) индексируют Unicode code points,
не байты UTF-8 и не UTF-16 code units. substring использует [begin,end).
Один символьный литерал — ровно одна Unicode scalar value. Поддержать
экранирование \n, \t, \\, \", \', \uXXXX для несуррогатных значений.
Некорректный UTF-8 и непарные суррогаты отклонять.

String поддерживает length(), charAt(), substring(), equals(), конкатенацию
+, String.valueOf() для восьми примитивов, интернирование одинаковых
литералов и String +=. null при конкатенации со String даёт строку "null".
== для String сравнивает ссылочную идентичность, equals — содержимое.
Unicode-нормализация не производится. Вывод String/char — UTF-8.
Для символов вне BMP результаты length/charAt могут отличаться от JVM;
это документированное различие, особенно важное в сравнительных тестах.

# 12. Классы и объекты

## 12.1. Конструкторы

Поддерживаются обычные конструкторы и перегрузка по точному совпадению
типов аргументов. Отсутствие пользовательских конструкторов создаёт
конструктор по умолчанию. Конструктор начинает с явного super(args) либо
неявного super(), если родитель имеет доступный конструктор без аргументов.
Синтаксис super.Parent(...) не поддерживать. Инициализация полей выполняется
после конструктора родителя, до тела конструктора текущего класса.

## 12.2. Поля

Поддерживаются public/protected/private/package-private, final и static.
Для ссылочных статических полей генератор создаёт единый массив
void *globals[N]; каждому полю соответствует стабильный индекс.
Все элементы globals инициализируются NULL и являются корнями GC.
Статические примитивные поля хранятся отдельно в соответствующих C99-типах.
Доступ к полю: ClassName.field; проверять static, модификаторы и final.
Инициализация классов — однократная, состояния UNINITIALIZED,
INITIALIZING, INITIALIZED. Родитель инициализируется до потомка,
статические инициализаторы полей выполняются в порядке объявления.
Обычные поля получают значения по умолчанию до пользовательской инициализации.

## 12.3. Методы

Методы экземпляра виртуальны по умолчанию, кроме final и специальных
случаев. Поддерживаются перегрузка, override, abstract, final, this,
super.method() и динамическая диспетчеризация по единственной цепочке
классов. Перегрузка — точное совпадение типов аргументов; при отсутствии
однозначного кандидата — ошибка. Неявные типовые преобразования запрещены.
Пользовательские static-методы, кроме main, пока не поддерживаются;
встроенные System.out/Math/String.valueOf — специальные Runtime API.

## 12.4. Object

Object — общий корневой класс для всех классов, строк и массивов.
У каждого полного объекта один заголовок Object и одна динамическая
идентичность. Объектные ссылки в C — void*. Приведение к Object всегда
однозначно, но из-за строгих правил типов требует явного cast.
Минимальный Object API: String toString(), boolean equals(Object),
final Class getClass(). Встроенный final Class имеет String getName().
Виртуальные toString/equals определяются по единственной цепочке
переопределений, getClass возвращает фактический динамический тип.
Object.toString по умолчанию — имя класса, @ и идентификатор аллокации
в шестнадцатеричном формате.

## 12.5. Abstract и final

Нельзя создавать экземпляр abstract-класса.

Конкретный класс обязан реализовать все обязательные абстрактные методы.

Нельзя наследоваться от final-класса.

Нельзя переопределять final-метод.

Нельзя изменять final-поле после разрешённой инициализации.

# 13. Garbage Collector: Mark-and-Sweep и точные корневые кадры

Управляемые объекты: экземпляры классов, String, массивы, Throwable и
другие объекты Runtime, содержащие managed ссылки. Все объекты
регистрируются в реестре выделений с размером, метаданными и mark bit.
Полную сборку запускать перед каждой управляемой аллокацией. Поддерживать
циклические графы; финализаторы не реализовывать. При нехватке памяти —
диагностируемая ошибка OutOfMemory и ненулевое завершение.

## 13.1. Корни

Отказаться от консервативного сканирования системного стека, setjmp,
NtCurrentTeb и Windows-специфичных механизмов. Корни — все слоты
void *globals[N] плюс явная цепочка кадров root stack по указателю
runtime `void **rets`. Каждый кадр существует в автоматической памяти
соответствующей сгенерированной функции.

Кадр имеет формат:
  frame[0] = (void*) previous_rets;
  frame[1..k] = живые объектные ссылки или NULL;
  frame[k+1] = (void*) frame;  // терминатор-самоссылка
  rets = frame;

Логический обход:
  void **frame = rets;
  while (frame != NULL) {
      for (size_t i = 1; frame[i] != (void*)frame; ++i)
          gc_mark_reference(frame[i]);
      frame = (void**)frame[0];
  }

Требуется также известный размер/capacity кадра, чтобы повреждённая
самоссылка не приводила к неограниченному чтению памяти. Терминатор
проверяется по отдельному descriptor/root_count. Нельзя случайно
принять объектную ссылку на сам кадр за конец.

Генератор обязан регистрировать this, ссылочные параметры, локальные
переменные, временные выражения, результаты new и возвращаемые ссылки.
Перед каждым потенциальным запуском GC все живые значения должны
находиться в зарегистрированных слотах или globals. Удалять кадр при
любом return; не допускать выхода из области жизни frame, пока rets
указывает на него. При return ссылка должна быть сохранена у caller
до следующей аллокации. Для throw без catch допускается завершающая
обработка Runtime, но все ссылки нужны до печати диагностики.

## 13.2. Mark

Сначала просканировать globals[0..N-1], затем все корневые кадры rets.
Каждую ненулевую managed-ссылку проверить по реестру, пометить объект,
поместить в явный worklist. Обходить точные смещения ссылочных полей,
ссылочные элементы одномерных массивов; примитивы не сканировать.
Повторно помеченные объекты пропускать.

## 13.3. Sweep

Освободить все немаркированные объекты, удалить их из реестра,
сбросить mark bits у выживших. Ложные удержания от произвольных
слов системного стека больше не допускаются, поскольку корни точные.
Генератор должен проходить анализ живости ссылок на каждом safepoint.

## 13.4. Исключения и throw

Поддержать оператор `throw expression;` и встроенные классы Throwable,
Exception, RuntimeException (конструкторы без аргументов и с String,
getMessage(), toString()). Пользовательские наследники Throwable допустимы.
Тип выражения при throw должен быть Throwable-подтипом или null.
Без try/catch/finally любой throw немедленно завершает программу
с ненулевым кодом и диагностикой имени динамического типа и сообщения.
throw null — контролируемая runtime-ошибка NullPointer. Для анализа
достижимости throw завершает путь. Допускается синтаксис `throws T1,T2`
в декларации метода, без реализации проверяемых исключений.

# 14. Runtime

Runtime реализуется отдельно на C99.

Компоненты:

- управление объектами;
- заголовок объекта;
- метаданные динамического типа;
- информация о единственном родительском классе;
- единый заголовок Object;
- VTable;
- таблицы интерфейсной диспетчеризации;
- выделение памяти;
- GC;
- строки;
- массивы;
- проверки типов;
- арифметические helpers;
- проверки границ;
- проверки null;
- обработка runtime errors;
- вывод данных.

## 14.1. Object metadata

Метаданные должны содержать информацию для:

- проверки типа;
- `instanceof`;
- приведений;
- определения динамического класса;
- обхода единственной цепочки классов и графа интерфейсов;
- интерфейсных проверок;
- виртуальной диспетчеризации.

Повторяющихся базовых подобъектов нет: у каждого класса не более одного
непосредственного родителя. Object хранится только один раз.

## 14.2. String

Реализуй:

- создание;
- длину;
- charAt;
- substring;
- equals;
- concat;
- преобразование примитивов;
- печать.

Внутреннее представление — UTF-8, а индексы методов — Unicode code points.

## 14.3. Массивы

Реализуй одномерные массивы всех поддерживаемых типов.

Обеспечь:

- хранение длины;
- проверку границ;
- значения по умолчанию;
- хранение ссылочных элементов;
- runtime-проверки типов;
- взаимодействие с GC.

## 14.4. System.out

Поддержи:

- `System.out.print`;
- `System.out.println`.

Для всех примитивных типов, String и объектных ссылок.

Печать объектов должна использовать согласованный механизм `toString()` через единый Object.

Определи точные форматы вывода чисел, boolean, char, null, NaN и Infinity.

## 14.5. Math

Минимальный API:

- abs;
- min;
- max;
- sqrt;
- pow;
- sin;
- cos;
- необходимые математические константы.

Не объявляй функции поддерживаемыми до реализации их семантики.

Если используются системные математические функции C, проверь совместимость с целевой средой и корректно организуй линковку.

## 14.6. Runtime errors

Ошибки времени выполнения содержат:

- тип ошибки;
- понятное сообщение;
- контекст, если доступен;
- ненулевой код завершения.

Минимальные ошибки:

- null dereference;
- array index out of bounds;
- division by zero;
- failed cast;
- invalid array store;
- out of memory;
- invalid runtime type operation.

Исключения Java не поддерживаются.

# 18. Генерация ANSI C99

Генератор получает только проверенный типизированный IR.
Все объектные ссылки — void* (в полях, параметрах, результатах,
массивах, временных значениях и globals). Тип Java сохраняется
семантикой и Runtime-метаданными. Запрещено приводить void* к
несовместимым указателям на функции: использовать типизированные
thunk-обёртки или единый корректный ABI вызова.

## 18.1. Объекты и метаданные

Каждый объект имеет общий header с фактическим динамическим классом.
Одна VTable на класс; отдельные интерфейсные таблицы. Нет ветвевых
VTable или повторных базовых подобъектов. При доступе к полю void*
преобразуется к соответствующей физической структуре только в
проверенном accessor. Метаданные описывают ссылочные поля для GC.

## 18.2. Статические поля и root frames

Генерировать void *globals[N] и детерминированные индексы ссылочных
static-полей. Примитивные static-поля — отдельно. Все ссылочные
значения в локальном C-коде должны иметь управляемые root slots.
IR содержит операции установки/снятия root frame и временных ссылок.
Учитывать корректный порядок вычислений Java независимо от C.

## 18.3. Генерация имён

Детерминированный name mangling кодирует класс, метод, типы
параметров и конструкторы. Не допускать коллизий с Runtime.
Все C-идентификаторы соответствуют C99; Java-идентификаторы ASCII-only.

## 18.4. Соблюдение C99

Корректные прототипы, включения заголовков, стандартные fixed-width
типы и переносимые операции. Не использовать Windows API, compiler-only
extensions и UB. Проверять сборку как минимум в режиме C99 с
pedantic-errors на доступном компиляторе; архитектура не должна
требовать конкретного GCC.

# 19. Диагностика

Диагностика содержит:

- тип ошибки;
- имя файла;
- строку;
- столбец;
- фрагмент исходника;
- описание;
- ожидаемый тип или конструкцию, если применимо.

Разделяй:

- лексические ошибки;
- синтаксические ошибки;
- ошибки типов;
- семантические ошибки;
- ошибки генерации;
- runtime errors.

Не выводи необработанный Python traceback как обычную диагностику программы пользователя.

Внутренние ошибки компилятора должны быть отличимы от ошибок исходной программы.

Разработчик отвечает за внутренние тесты, интеграционные тесты и регрессионные тесты.

## 20.5. Runtime

Проверяй выделение и освобождение, достижимые и недостижимые объекты,

Для каждого теста:

1. Сгенерировать C.
2. Проверить C99-синтаксис GCC в режиме C99.
3. Слинковать с runtime.
4. Запустить программу.
5. Проверить ожидаемый результат.

Не считай успешную генерацию текста C достаточным результатом.

Добавляй регрессионные тесты на каждую обнаруженную ошибку.

# 24. Критерии готовности

Проект готов, когда Lexer читает UTF-8 и отвергает Unicode-идентификаторы;
Parser строит AST согласованной грамматики; семантика обнаруживает ошибки;
работают восемь примитивов, строгие преобразования, String UTF-8,
одномерные массивы, классы, ОДИНОЧНОЕ наследование классов,
МНОЖЕСТВЕННОЕ наследование интерфейсов, abstract/final,
конструкторы, перегрузка, виртуальные/интерфейсные вызовы;
throw завершает программу без try/catch; static reference поля
доступны через globals[N]; все объектные ссылки компилируются в void*;
Mark-and-Sweep с точными корневыми кадрами rets корректно сохраняет
живые и освобождает недостижимые объекты; сгенерированный C99
компилируется совместно с Runtime без Windows API; интеграционные
и регрессионные тесты проходят, README соответствует реализации.

# 25. Итоговое требование

Создай полноценный модульный и тестируемый учебный компилятор
подмножества Java в ISO C99. Главные приоритеты: семантическая
корректность, типизация, одиночное наследование классов, множественное
наследование интерфейсов, UTF-8, portable Runtime, точный Mark-and-Sweep
с цепочкой rets, надёжная диагностика и отсутствие фиктивной поддержки.
Работай по этапам, проверяя реализованное кодом и тестами. Не меняй
зафиксированную семантику молча.
