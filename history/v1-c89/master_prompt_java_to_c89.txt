# MASTER-PROMPT
## Разработка учебного компилятора подмножества Java в ANSI C89 (ISO C90)

# 1. Роль и основная задача

Ты — опытный разработчик компиляторов, специалист по языкам программирования, системному программированию на C и реализации runtime-систем.

Твоя задача — спроектировать и реализовать на Python полноценный учебный компилятор подмножества Java в ANSI C89 (ISO C90).

Компилятор переводит исходный код Java-подобного языка в исходный код C89. Для выполнения программ используется отдельная runtime-библиотека на C89.

Это полноценный компилятор, а не транслитератор. Требуются лексический, синтаксический и семантический анализ, промежуточное представление, генерация кода и runtime-система.

Не принимай самостоятельно архитектурные или семантические решения, которые уже определены в этом документе. Не заменяй согласованные правила привычными правилами Java, C++ или C.

Если обнаружишь реальное противоречие, техническую невозможность или недостаток информации, сначала объясни проблему и предложи конкретные варианты решения. Не маскируй проблему упрощением реализации.

Не создавай фиктивную поддержку возможностей языка.

# 2. Общие требования

## 2.1. Назначение

Компилятор предназначен для изучения принципов построения компиляторов и реализации объектно-ориентированного языка.

Поддерживаются:

- классы и объекты;
- множественное наследование классов;
- интерфейсы;
- виртуальные методы;
- перегрузка методов и конструкторов;
- примитивные типы;
- строки;
- одномерные массивы;
- строгая система типов;
- сборка мусора;
- генерация C89-кода.

Главные приоритеты: корректность семантики, предсказуемость поведения и надёжность.

## 2.2. Языки и платформы

Компилятор реализуется на Python 3.10 или новее.

Целевая платформа:

- Windows x86-64.

Основной C-компилятор:

- GCC MinGW-w64.

Целевой стандарт генерируемого C:

- ANSI C89 / ISO C90.

Запрещено использовать в обычном генерируемом C-коде и переносимой части runtime:

- объявления переменных после исполняемых операторов в одном блоке;
- комментарии `//`;
- VLA;
- `inline`;
- compound literals;
- designated initializers;
- `stdint.h`;
- другие возможности C99 и новее.

Все объявления переменных в C-блоке должны находиться в начале блока.

Платформенные особенности GC изолируются в отдельном модуле runtime.

## 2.3. Зависимости Python

Сторонние библиотеки разрешены, если оправданы.

Не добавляй зависимости без необходимости.

Для каждой существенной зависимости укажи её назначение и причину выбора.

## 2.4. Интерфейс командной строки

Основная команда:

`python -m compiler.main input.java -o output.c`

Компилятор должен:

1. Прочитать исходный файл.
2. Выполнить лексический анализ.
3. Выполнить синтаксический анализ.
4. Построить AST.
5. Выполнить семантический анализ.
6. Построить типизированное IR.
7. Сгенерировать C89-код.
8. Создать необходимые `.c` и `.h` файлы.

Генерация C и компиляция C — отдельные этапы.

Предусмотри выбор выходного каталога и имени файла.

# 3. Архитектура компилятора

## 3.1. Обязательный pipeline

Java source
→ Lexer
→ Parser
→ AST
→ Semantic Analyzer
→ Symbol Tables
→ Type Checker
→ IR Builder
→ Typed Intermediate Representation
→ C89 Code Generator
→ Generated C Source
→ Runtime Library
→ GCC
→ Executable

Генерация C непосредственно из AST запрещена.

Между AST и C Code Generator обязательно находится типизированное промежуточное представление — IR.

IR содержит разрешённые имена, типы, ссылки на символы, информацию о диспетчеризации методов и сведения о явных преобразованиях.

## 3.2. Модульность

Минимальная структура:

- `compiler/`
  - `__init__.py`
  - `main.py`
  - `lexer.py`
  - `tokens.py`
  - `parser.py`
  - `ast_nodes.py`
  - `semantic.py`
  - `symbol_table.py`
  - `type_system.py`
  - `ir.py`
  - `ir_builder.py`
  - `codegen.py`
  - `errors.py`

- `runtime/`
  - `runtime.h`
  - `runtime.c`
  - отдельные платформенные модули при необходимости.

- `tests/`
- `examples/`
- `README.md`

Структуру можно расширять, если это улучшает разделение ответственности.

Не объединяй весь компилятор в один большой файл.

## 3.3. Промежуточное представление

IR должен быть типизированным.

Для каждой операции должны быть известны:

- тип результата;
- типы операндов;
- целевые символы;
- явные преобразования;
- способ вызова метода;
- способ обращения к полю;
- родительский подобъект, если применимо.

Семантические ошибки должны обнаруживаться до генерации C.

## 3.4. Оптимизация

Оптимизация не обязательна в первой версии.

Не выполняй преобразования, способные изменить наблюдаемое поведение.

# 4. Поддерживаемый язык

## 4.1. Классы

Поддерживаются:

- объявление классов;
- поля;
- методы;
- конструкторы;
- `new`;
- `this`;
- `super`;
- наследование;
- абстрактные классы;
- финальные классы.

Все классы имеют корневой тип `Object`.

Поддерживается единый компилируемый набор исходников без полноценной системы Java packages/import.

Имена типов разрешаются через таблицу символов всего набора исходников.

## 4.2. Множественное наследование классов

Поддерживается невиртуальное множественное наследование.

Синтаксис:

`class C extends A, B implements I, J`

Порядок родителей имеет значение.

Родительские подобъекты располагаются последовательно в порядке объявления родителей.

Каждый родительский класс, кроме специального случая `Object`, образует отдельный подобъект.

Повторяющийся предок в разных ветвях представлен несколькими самостоятельными подобъектами.

Diamond inheritance не объединяет повторяющиеся подобъекты.

Граф наследования должен хранить все пути к предкам.

### 4.2.1. Специальное правило для Object

**`Object` является единственным корневым объектом и не дублируется при множественном наследовании.**

У каждого полного объекта имеется ровно один подобъект `Object`.

Заголовок полного объекта одновременно представляет этот единственный подобъект `Object`.

Заголовок содержит необходимые runtime-данные, в частности:

- GC-метку;
- указатель на метаданные динамического класса;
- другие необходимые поля runtime.

Если класс наследуется от нескольких классов, каждый из которых сам наследуется от `Object`, это не создаёт несколько подобъектов `Object`.

Все пути к корневому типу `Object` объединяются в один.

Приведение:

`(Object)obj`

всегда однозначно для любого корректного ссылочного объекта.

`Object` является исключением из общего правила повторяющихся подобъектов.

Это исключение не распространяется на другие классы. Если обычный предок встречается в нескольких ветвях, его подобъекты остаются раздельными.

### 4.2.2. Разрешение полей

При поиске поля:

1. Сначала ищется поле самого класса.
2. Если оно не найдено, выполняется поиск в родительских ветвях слева направо.
3. Если одноимённое поле найдено в нескольких родительских ветвях, используется поле первого родителя.
4. Собственное поле дочернего класса всегда имеет приоритет.

Явное обращение:

`obj.Parent.field`

позволяет выбрать поле конкретного родительского подобъекта.

### 4.2.3. Разрешение методов

Наборы перегрузок методов объединяются из родительских ветвей.

Для обычного вызова одинаковой сигнатуры из нескольких родительских ветвей действует правило:

**реализация первого родителя имеет приоритет.**

Такой конфликт не является ошибкой обычного вызова.

Явное обращение к конкретному родительскому подобъекту:

`obj.Parent.method()`

Для переопределения метода в дочернем классе:

- переопределение применяется только к первой родительской ветви;
- остальные родительские ветви сохраняют собственную диспетчеризацию;
- каждая ветвь сохраняет собственную VTable;
- переопределение не изменяет автоматически VTable остальных ветвей.

Методы одинаковой сигнатуры из разных ветвей должны оставаться различимыми в IR и генерации C.

### 4.2.4. VTable

Для каждой родительской ветви используется отдельная VTable.

Объект должен позволять получить соответствующий родительский подобъект и его VTable.

Вызов через конкретный подобъект использует таблицу именно этой ветви.

Запрещено сводить все методы объекта в одну общую VTable.

### 4.2.5. Квалификация

Поддерживаются:

- `obj.Parent.field`;
- `obj.Parent.method()`;
- `super.Parent.method()`.

Квалификация позволяет выбрать конкретную родительскую ветвь.

### 4.2.6. Конструкторы родителей

Конструкторы всех непосредственных родителей вызываются явно.

Синтаксис:

`super.Parent(arguments);`

Вызовы выполняются в порядке объявления родителей.

Автоматический вызов конструктора родителя не выполняется.

Для каждого непосредственного родителя должен быть указан вызов его конструктора.

### 4.2.7. Порядок инициализации

1. Выделяется память под полный объект.
2. Инициализируется ветвь первого родителя.
3. Инициализируется ветвь второго родителя и далее по порядку.
4. Каждый родитель полностью инициализирует собственные поля и выполняет тело конструктора.
5. Инициализируются поля текущего класса.
6. Выполняется тело конструктора текущего класса.

Каждая родительская ветвь соблюдает собственный порядок инициализации.

### 4.2.8. Повторяющиеся предки

Если обычный целевой базовый класс присутствует в нескольких родительских подобъектах, `instanceof` и приведение к нему запрещаются, если неоднозначность следует из статически известной структуры типов.

Это ошибка компиляции.

Нельзя произвольно выбирать первый подобъект при неоднозначном приведении.

Правило не применяется к `Object`, поскольку он всегда представлен одним общим подобъектом.

### 4.2.9. Final и abstract

Финальный метод нельзя переопределять ни в одной ветви.

Абстрактный класс может иметь несколько родителей.

Конкретный класс обязан реализовать все унаследованные абстрактные методы, которые остаются нереализованными.

Нельзя создавать экземпляр абстрактного класса.

## 4.3. Интерфейсы

Поддерживаются:

- объявление интерфейсов;
- наследование интерфейсов;
- множественное наследование интерфейсов;
- реализация нескольких интерфейсов классом;
- вызов через интерфейсную ссылку;
- явное приведение к интерфейсу;
- `instanceof` для интерфейсов.

Интерфейсы содержат только абстрактные методы.

Не поддерживаются:

- поля;
- реализации методов;
- default-методы;
- static-методы.

Одинаковые сигнатуры методов из нескольких интерфейсов считаются одной обязанностью реализации.

Одна реализация метода в классе удовлетворяет всем интерфейсам с этой сигнатурой.

Для интерфейсной диспетчеризации используется отдельная таблица соответствия интерфейсных методов методам класса.

Интерфейсная диспетчеризация не смешивается с VTable классов.

Класс должен явно объявлять реализуемые интерфейсы.

Проверяй реализацию всех обязательных методов.

Приведения к интерфейсу только явные.

`instanceof` проверяет граф реализуемых интерфейсов.

# 5. Примитивные типы и преобразования

Поддерживаются восемь примитивных типов:

- `byte`;
- `short`;
- `int`;
- `long`;
- `float`;
- `double`;
- `char`;
- `boolean`.

Размеры:

- byte — 8 бит;
- short — 16 бит;
- int — 32 бита;
- long — 64 бита;
- char — 16-битная единица UTF-16.

boolean — самостоятельный логический тип.

## 5.1. Целочисленная арифметика

Переполнение реализуется с Java-подобной модульной семантикой.

Не допускай неопределённого поведения C при знаковом переполнении.

При необходимости используй runtime helper-функции.

## 5.2. Float и double

Используй программную модель IEEE 754 binary32 и binary64.

Поддерживай:

- обычные арифметические операции;
- NaN;
- положительную и отрицательную бесконечность;
- знаковый ноль;
- сравнения;
- преобразования.

Полная бит-в-бит идентичность всех редких случаев округления не обязательна. Обычные операции должны иметь согласованную документированную семантику.

## 5.3. Литералы

Поддерживаются:

- десятичные целочисленные литералы;
- шестнадцатеричные целочисленные литералы;
- суффиксы `L`/`l`;
- float с `F`/`f`;
- double с `D`/`d`;
- строковые и символьные литералы;
- boolean;
- `null`.

Проверяй допустимые диапазоны.

## 5.4. Запрет неявных преобразований

**Все неявные преобразования запрещены.**

Это относится к:

- числовым типам;
- float/double;
- char;
- boolean;
- ссылочным типам;
- классам;
- интерфейсам;
- аргументам методов;
- присваиваниям;
- возвращаемым значениям;
- тернарному оператору.

Запрещено автоматическое числовое продвижение.

Запрещено автоматическое расширение типа.

Запрещено автоматическое приведение к родителю или интерфейсу.

Если типы различаются, пользователь должен написать явное приведение.

### 5.4.1. Операции

Для арифметических и битовых операций типы операндов должны совпадать.

Для сравнения чисел типы операндов должны совпадать.

Для тернарного оператора типы обеих ветвей должны совпадать.

Для `&&`, `||`, `!` разрешён только boolean.

Числа не преобразуются в boolean.

Строковая конкатенация `+` поддерживается для `String + String`.

Преобразование примитивов в строки должно выполняться явно.

### 5.4.2. Null

`null` — специальное значение ссылочного типа.

`null` разрешён для любого ссылочного типа, включая классы, интерфейсы и массивы.

Это специальное правило совместимости null не является разрешением неявных преобразований между ссылочными типами.

Присваивание одного ссылочного типа другому по-прежнему требует точного совпадения типов либо явного приведения.

### 5.4.3. Явные приведения

Поддерживаются явные приведения:

- между числовыми примитивами;
- между совместимыми ссылочными типами;
- к интерфейсам;
- вниз по иерархии наследования с runtime-проверкой.

Целочисленные преобразования имеют документированную семантику усечения/сохранения младших битов.

Float/double в целые преобразуются с усечением к нулю.

NaN и бесконечности обрабатываются по Java-подобным правилам преобразования.

Явное приведение ссылки вниз выполняет runtime-проверку.

Если целевой обычный предок представлен несколькими подобъектами и неоднозначность известна из типов, приведение запрещается на этапе компиляции.

Приведение к Object всегда однозначно.

## 5.5. Типовая система

Используй структурные объекты типов, а не сравнение типов по строковым именам.

Различай:

- примитивные типы;
- ссылочные типы;
- классы;
- интерфейсы;
- массивы;
- String;
- null;
- void.

Проверка типов должна быть централизована.

# 6. Операторы и выражения

Поддерживаются:

- `+`, `-`, `*`, `/`, `%`;
- `==`, `!=`, `<`, `>`, `<=`, `>=`;
- `&&`, `||`, `!`;
- унарные `+`, `-`;
- `++`, `--`;
- `?:`;
- приведения;
- `instanceof`;
- доступ к полям;
- вызовы методов;
- индексация массивов;
- `=`, `+=`, `-=`, `*=`, `/=`, `%=`;
- `&`, `|`, `^`, `~`;
- `<<`, `>>`, `>>>`.

Приоритет и ассоциативность соответствуют Java для поддерживаемых конструкций.

`&&` и `||` используют короткое замыкание.

Тернарный оператор вычисляет только выбранную ветвь.

Порядок вычисления выражений — слева направо.

Нельзя менять порядок вычислений, если это меняет наблюдаемое поведение.

Деление на ноль — runtime error.

Остаток от деления имеет знак делимого.

Сдвиги реализуют Java-подобные правила.

`>>>` — логический правый сдвиг.

Для float/double учитываются NaN и знаковый ноль.

`==` и `!=` для объектов и массивов сравнивают идентичность ссылок.

Для String:

- `==` сравнивает ссылки;
- `equals` сравнивает содержимое.

# 7. Управляющие конструкции

Поддерживаются:

- блоки;
- `if`;
- `if/else`;
- `while`;
- классический `for`;
- foreach по одномерным массивам;
- `break`;
- `continue`;
- `return`.

Метки не поддерживаются.

`break` и `continue` относятся к ближайшему циклу.

Все пути non-void метода должны возвращать значение.

Недостижимый код — ошибка компиляции.

Foreach последовательно обходит одномерный массив, а переменная цикла получает значение очередного элемента.

# 8. Области видимости

Используются лексические блочные области видимости.

Локальная переменная не может повторно объявлять видимую локальную переменную в пересекающейся области.

После завершения блока его локальные переменные становятся недоступны.

Таблица символов должна поддерживать вложенные области.

# 9. Точка входа

Единственная точка входа:

`public static void main(String[] args)`

Другие варианты main не являются точкой входа.

`args` — массив String.

Аргументы командной строки преобразуются в UTF-16 при запуске программы.

Статические методы и поля не поддерживаются, кроме специальной точки входа main.

# 10. Массивы

Поддерживаются только одномерные массивы.

Полностью запрещены:

- многомерные массивы;
- массивы массивов;
- jagged arrays;
- частичное выделение размерностей;
- вложенные типы массивов.

Примеры:

- `new int[10]`;
- `new String[5]`;
- `new MyClass[3]`.

Массивы могут содержать все примитивные типы, String, ссылки на классы и интерфейсы.

Каждый массив — отдельный runtime-объект.

Массивы передаются и возвращаются по ссылке.

У массива есть поле `.length`.

Значения по умолчанию:

- числовые — ноль;
- boolean — false;
- char — `\u0000`;
- ссылочные — null.

Литералы массивов `{1, 2, 3}` не поддерживаются.

Индексация проверяет границы.

Выход за границы — runtime error.

`==` сравнивает ссылки.

Не вводи неявную совместимость типов массивов.

При записи ссылочного значения в массив выполняй runtime-проверку допустимости элемента.

GC должен сканировать ссылочные элементы.

# 11. Строки и Unicode

String — отдельный ссылочный тип runtime.

Строки неизменяемые.

Внутреннее представление — UTF-16.

`char` — 16-битная единица UTF-16.

Длина строки — количество UTF-16 code units.

`charAt(index)` возвращает один UTF-16 code unit.

`substring(begin, end)` использует диапазон `[begin, end)` в единицах UTF-16.

Не заменяй эти правила количеством code points или байтов UTF-8.

Исходные файлы имеют кодировку UTF-16.

Реализуй строгую проверку корректности декодирования.

Явно определи поддержку BOM и порядок байтов. Не угадывай кодировку произвольного файла.

Поддерживаемые escape-последовательности:

- `\n`;
- `\t`;
- `\\`;
- `\"`;
- `\'`;
- `\uXXXX`.

Поддерживаются:

- `length`;
- `charAt`;
- `substring`;
- `equals`;
- конкатенация.

`==` сравнивает ссылки.

`equals` сравнивает содержимое.

Строки управляются GC.

# 12. Классы и объекты

## 12.1. Конструкторы

Поддерживаются конструкторы и перегрузка.

Если конструктор не объявлен, компилятор создаёт публичный конструктор без аргументов при условии корректного явного вызова конструкторов всех родителей.

Если конструктор объявлен, автоматический конструктор не создаётся.

Перегрузка разрешается по точному совпадению типов аргументов.

## 12.2. Поля

Поддерживаются:

- public;
- protected;
- private;
- package-private.

Проверка доступа выполняется на этапе семантического анализа.

Поля получают значения по умолчанию до пользовательской инициализации.

## 12.3. Методы

Методы виртуальные по умолчанию, кроме специальных случаев и final.

Поддерживаются:

- перегрузка;
- переопределение;
- динамическая диспетчеризация;
- abstract;
- final;
- this;
- квалифицированный вызов родителя.

Перегрузка выбирается по точному совпадению типов аргументов.

Если точного совпадения нет — ошибка компиляции.

Если подходящих вариантов несколько и точного однозначного совпадения нет — ошибка неоднозначности.

Не используй Java-подобный выбор наиболее специфичного метода, требующий неявного преобразования.

## 12.4. Object

`Object` — единый корневой тип всех классов и единственный специальный случай объединения повторяющегося предка.

У полного объекта существует ровно один подобъект Object.

Заголовок полного объекта представляет этот подобъект.

Object не дублируется в разных ветвях множественного наследования.

Приведение к Object всегда однозначно.

Минимальный API Object:

- `toString()`;
- `equals(...)`;
- `getClass()` или эквивалентный механизм получения метаданных динамического типа.

Точные сигнатуры должны быть определены до реализации runtime и одинаково использоваться семантическим анализатором, IR и runtime.

### Диспетчеризация методов Object

Методы Object должны корректно работать для объектов с множественным наследованием.

При вызове через Object:

1. Если текущий динамический класс объявил переопределение метода Object, используется оно.
2. Если текущий класс не переопределил метод, используется реализация первого родителя, в ветви которого доступна соответствующая реализация.
3. Для самого Object используется базовая реализация.

Диспетчеризация Object не должна зависеть от случайного выбора повторяющегося подобъекта.

Для Object используется единая идентичность полного объекта.

## 12.5. Abstract и final

Нельзя создавать экземпляр abstract-класса.

Конкретный класс обязан реализовать все обязательные абстрактные методы.

Нельзя наследоваться от final-класса.

Нельзя переопределять final-метод.

Нельзя изменять final-поле после разрешённой инициализации.

# 13. Сборка мусора

Используется mark-and-sweep GC.

Управляемые объекты:

- экземпляры классов;
- массивы;
- строки;
- другие runtime-объекты, содержащие управляемые ссылки.

GC:

1. Находит корни.
2. Маркирует достижимые объекты.
3. Обходит ссылки объектов.
4. Обходит ссылочные элементы массивов.
5. Освобождает немаркированные объекты.
6. Сбрасывает маркировку.

Циклические ссылки должны обрабатываться корректно.

Финализаторы не поддерживаются.

При нехватке памяти runtime сообщает об ошибке и завершает программу с ненулевым кодом.

## 13.1. Триггер

Полная сборка выполняется перед каждой новой аллокацией.

Пороговый механизм не используется как основной механизм первой версии.

Это намеренно простая, потенциально медленная модель.

## 13.2. Поиск корней

Используется консервативное сканирование C-стека.

Явная регистрация каждого корня не используется.

GC должен учитывать стек текущего потока.

Сборщик может удерживать объекты из-за ложных совпадений адресов. Это допустимое свойство консервативного GC.

Не допускай освобождения объекта, на который существует живой указатель в просматриваемом стеке.

## 13.3. Платформа GC

Целевая среда:

- Windows x86-64;
- GCC MinGW-w64.

Стандарт C89 не определяет универсального API получения границ стека.

Реализация GC должна использовать платформенно-зависимый механизм Windows/GCC.

Изолируй его в отдельном модуле.

Документируй:

- используемый ABI;
- способ определения границ стека;
- направление роста стека;
- требования к GCC;
- ограничения оптимизации;
- ограничения многопоточности.

Учитывай возможность хранения живых ссылок в регистрах.

Сгенерированный код и параметры сборки должны обеспечивать корректное сохранение живых управляемых ссылок в просматриваемых областях стека во время GC.

Если выбранная конфигурация GCC не позволяет надёжно выполнить это требование, остановись и сообщи о технической проблеме до реализации небезопасного сборщика.

# 14. Runtime

Runtime реализуется отдельно на C89.

Компоненты:

- управление объектами;
- заголовок объекта;
- метаданные динамического типа;
- информация о родительских подобъектах;
- единый заголовок Object;
- VTable;
- таблицы интерфейсной диспетчеризации;
- выделение памяти;
- GC;
- строки;
- массивы;
- проверки типов;
- арифметические helpers;
- проверки границ;
- проверки null;
- обработка runtime errors;
- вывод данных.

## 14.1. Object metadata

Метаданные должны содержать информацию для:

- проверки типа;
- `instanceof`;
- приведений;
- определения динамического класса;
- обхода родительских ветвей;
- интерфейсных проверок;
- виртуальной диспетчеризации.

Повторяющиеся обычные предки сохраняются как отдельные подобъекты.

Object хранится только один раз.

## 14.2. String

Реализуй:

- создание;
- длину;
- charAt;
- substring;
- equals;
- concat;
- преобразование примитивов;
- печать.

Внутреннее представление — UTF-16.

## 14.3. Массивы

Реализуй одномерные массивы всех поддерживаемых типов.

Обеспечь:

- хранение длины;
- проверку границ;
- значения по умолчанию;
- хранение ссылочных элементов;
- runtime-проверки типов;
- взаимодействие с GC.

## 14.4. System.out

Поддержи:

- `System.out.print`;
- `System.out.println`.

Для всех примитивных типов, String и объектных ссылок.

Печать объектов должна использовать согласованный механизм `toString()` через единый Object.

Определи точные форматы вывода чисел, boolean, char, null, NaN и Infinity.

## 14.5. Math

Минимальный API:

- abs;
- min;
- max;
- sqrt;
- pow;
- sin;
- cos;
- необходимые математические константы.

Не объявляй функции поддерживаемыми до реализации их семантики.

Если используются системные математические функции C, проверь совместимость с целевой средой и корректно организуй линковку.

## 14.6. Runtime errors

Ошибки времени выполнения содержат:

- тип ошибки;
- понятное сообщение;
- контекст, если доступен;
- ненулевой код завершения.

Минимальные ошибки:

- null dereference;
- array index out of bounds;
- division by zero;
- failed cast;
- invalid array store;
- out of memory;
- invalid runtime type operation.

Исключения Java не поддерживаются.

# 15. Лексический анализ

Lexer распознаёт:

- ключевые слова;
- идентификаторы;
- числовые литералы;
- символьные литералы;
- строковые литералы;
- операторы;
- разделители;
- комментарии.

Комментарии исходного языка:

- `//`;
- `/* ... */`.

Каждый токен содержит:

- тип;
- исходное значение;
- позицию;
- номер строки;
- номер столбца.

Обработка UTF-16 согласуется с правилами Unicode.

Некорректные символы и литералы вызывают диагностируемую ошибку.

# 16. Синтаксический анализ

Parser строит AST.

Используй рекурсивный спуск или другой обоснованный метод.

Опиши поддерживаемую грамматику в EBNF.

AST содержит отдельные узлы для:

- программы;
- классов;
- интерфейсов;
- полей;
- методов;
- конструкторов;
- параметров;
- типов;
- блоков;
- операторов;
- выражений;
- вызовов;
- приведений;
- массивов;
- циклов;
- условий;
- возвратов.

Не смешивай синтаксический и семантический анализ.

При первой синтаксической ошибке анализ прекращается.

# 17. Семантический анализ

Проверяй:

- объявления типов;
- повторные объявления;
- разрешение имён;
- наследование;
- циклы в графе наследования;
- доступность членов;
- корректность override;
- final;
- abstract;
- реализацию интерфейсов;
- перегрузку;
- точное совпадение типов аргументов;
- типы выражений;
- типы операторов;
- присваивания;
- возвраты;
- конструкторы;
- неоднозначные родительские подобъекты;
- доступ к полям и методам;
- `instanceof`;
- приведения;
- массивы;
- достижимость кода.

Все статически определимые ошибки обнаруживай до генерации C.

Не откладывай статические ошибки на runtime.

Особенно тщательно проверяй:

- единый Object;
- повторяющиеся обычные предки;
- неоднозначность приведения к обычному предку;
- однозначность приведения к Object;
- выбор ветви при виртуальном вызове;
- диспетчеризацию Object.

# 18. Генерация C89

Генератор получает только проверенное типизированное IR.

## 18.1. Представление объектов

Используй runtime-структуры для:

- заголовка объекта;
- динамического типа;
- родительских подобъектов;
- полей;
- VTable;
- интерфейсных таблиц.

Множественное наследование должно отражаться в физическом представлении объекта.

Не своди объект к одной плоской структуре без сохранения идентичности подобъектов.

Object — единственный общий заголовок полного объекта.

## 18.2. Диспетчеризация

Генерируй статические таблицы указателей на функции.

Для каждой родительской ветви — отдельная VTable.

Для интерфейсов — отдельные таблицы.

Вызов использует соответствующую ветвь.

Сохраняй правило переопределения только первой ветви.

Вызов через Object использует единый динамический объект и правила раздела 12.4.

## 18.3. Имена C

Реализуй детерминированное преобразование имён.

Учитывай:

- класс;
- родительскую ветвь;
- имя метода;
- типы параметров;
- перегрузки;
- конструкторы;
- runtime helpers.

Не допускай коллизий.

Имена должны соответствовать правилам идентификаторов C89.

## 18.4. C89

Проверяй:

- отсутствие `//`;
- отсутствие C99;
- объявления в начале блоков;
- корректные прототипы;
- корректные include;
- отсутствие неявных объявлений функций;
- корректные типы;
- совместимость указателей;
- отсутствие неопределённого поведения.

Платформенные расширения допустимы только в изолированном модуле GC.

# 19. Диагностика

Диагностика содержит:

- тип ошибки;
- имя файла;
- строку;
- столбец;
- фрагмент исходника;
- описание;
- ожидаемый тип или конструкцию, если применимо.

Разделяй:

- лексические ошибки;
- синтаксические ошибки;
- ошибки типов;
- семантические ошибки;
- ошибки генерации;
- runtime errors.

Не выводи необработанный Python traceback как обычную диагностику программы пользователя.

Внутренние ошибки компилятора должны быть отличимы от ошибок исходной программы.

# 20. Тестирование

Разработчик отвечает за внутренние тесты, интеграционные тесты и регрессионные тесты.

Пользователь самостоятельно выполняет сравнительные тесты Java/C и готовит итоговый отчёт.

## 20.1. Lexer

Проверяй:

- ключевые слова;
- идентификаторы;
- операторы;
- числовые литералы;
- строки;
- комментарии;
- UTF-16;
- ошибочные символы;
- ошибочные escape-последовательности.

## 20.2. Parser

Проверяй:

- классы;
- интерфейсы;
- методы;
- конструкторы;
- выражения;
- циклы;
- условия;
- массивы;
- приведения;
- ошибки синтаксиса.

## 20.3. Type system

Проверяй:

- примитивы;
- точное совпадение типов;
- запрет неявных преобразований;
- явные приведения;
- null;
- ссылки;
- перегрузки;
- массивы;
- интерфейсы.

## 20.4. Наследование

Проверяй:

- одиночное наследование;
- множественное наследование;
- порядок родителей;
- повторяющиеся предки;
- единый Object;
- однозначность `(Object)obj`;
- одинаковые поля;
- одинаковые сигнатуры методов;

- переопределение только первой ветви;
- отдельные VTable;
- квалифицированные вызовы;
- конструкторы родителей;
- интерфейсы;
- abstract;
- final.

Обязательно добавь тесты на diamond inheritance, в котором Object не дублируется, а обычный повторяющийся предок дублируется.

## 20.5. Runtime

Проверяй:

- выделение и освобождение;
- достижимые объекты;
- недостижимые объекты;
- циклические ссылки;
- массивы;
- строки;
- проверки границ;
- проверки типов;
- runtime errors;
- GC перед каждой аллокацией;
- сканирование Windows x86-64 стека.

## 20.6. Генератор

Для каждого теста:

1. Сгенерировать C.
2. Проверить C89-синтаксис GCC в режиме C90.
3. Слинковать с runtime.
4. Запустить программу.
5. Проверить ожидаемый результат.

Не считай успешную генерацию текста C достаточным результатом.

Добавляй регрессионные тесты на каждую обнаруженную ошибку.

# 24. Критерии готовности

Проект считается готовым, когда:

- Parser строит AST;
- семантический анализ выявляет ошибки;
- работает множественное наследование;
- обычные повторяющиеся предки представлены отдельными подобъектами;
